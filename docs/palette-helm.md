# Deploying HelloWorld via a Palette Helm registry (GitHub Pages)

The working path for getting our chart onto a Palette-managed EKS cluster.

## The controlling fact

The pod that downloads a chart is the `palette-controller-manager` running
**inside the target cluster**, not in the Palette management cluster. It uses
the target cluster's CoreDNS and network. So the Helm registry endpoint must
be reachable from every managed cluster that will consume the chart —
in-cluster Service DNS on the Palette side doesn't work.

That rules out:

- ChartMuseum deployed alongside Palette (its `*.svc.cluster.local` name
  doesn't resolve in the target cluster)
- Harbor at `http://harbor.harbor.svc.cluster.local` for the same reason

GitHub Pages is the simplest publicly-reachable Helm repo — no extra infra,
stable URL, versioned by git.

## The gh-pages branch of this repo *is* the Helm registry

```
gh-pages/
  helloworld-0.1.0.tgz        # packaged chart
  index.yaml                  # Helm repo index, generated by `helm repo index`
```

Served at:

```
https://bdecoste.github.io/systemd-helloworld/index.yaml
```

Pages is enabled with source = `gh-pages` branch, path = `/`.

## Publishing a new version

Bump `palette-helm/helloworld/Chart.yaml` (`version:`) on `main`, then
regenerate the gh-pages branch:

```bash
cd /Users/bill.decoste/claudecode/heart-flow

# Package the current chart from main
helm package palette-helm/helloworld -d /tmp

# Switch to gh-pages and add the new tarball
git checkout gh-pages
cp /tmp/helloworld-*.tgz .
helm repo index . --url "https://bdecoste.github.io/systemd-helloworld"
git add -A
git commit -m "Publish helloworld chart $(ls helloworld-*.tgz | sort -V | tail -1)"
git push origin gh-pages
git checkout main
```

Pages redeploys automatically on push (~30–60s).

Verify:

```bash
curl -sfL https://bdecoste.github.io/systemd-helloworld/index.yaml | head -20
```

## Register in Palette

Tenant Settings → Registries → Add Pack Registry → **Helm** (the classic
index.yaml-based sub-type, not OCI):

| Field         | Value                                                 |
|---------------|-------------------------------------------------------|
| Registry Name | `helloworld-github-pages`                             |
| Endpoint      | `https://bdecoste.github.io/systemd-helloworld`       |
| Auth          | none (public repo)                                    |

No sync button is expected — Palette's Helm HTTP sub-type queries the
registry on demand when the profile picker opens or when a cluster
reconciles.

## Add to a Cluster Profile

Profiles → Add New Profile → Add-on (AWS) → Add Pack → Registry:
`helloworld-github-pages` → `helloworld @ 0.1.0`.

**Override at minimum:**

```yaml
image:
  repository: <account>.dkr.ecr.<region>.amazonaws.com/helloworld
  tag: "0.1.0"
```

Otherwise pulls will `ImagePullBackOff` against the placeholder
`helloworld:0.1.0` tag that has no real ECR path.

Attach the profile to the EKS cluster. Track progress:

```bash
export KUBECONFIG=~/Downloads/decoste-eks-kubeconfig.yaml
kubectl get ns | grep -i hello
kubectl -n <ns> get all,cm,ingress
kubectl -n <ns> logs -l app.kubernetes.io/name=helloworld -f
```

Or on the Palette side:

```bash
kubectl -n cluster-<uid> logs -f deploy/palette-controller-manager \
  | grep -iE 'helloworld|helm|pack|error|reconcil'
```

## Appendix — paths tried, why they didn't work

- **Palette Pack OCI (Harbor + oras)** — `packsync` completes cleanly but
  reports "oci packs are empty" for user-provided Harbor registries.
  Apparently requires a Spectro-native manifest artifact
  (`containsSpectroManifest: true` on the working Palette public registry
  entry) that stock oras + Harbor can't produce.
- **Helm OCI (Harbor)** — chart pushes fine with the correct
  `application/vnd.cncf.helm.chart.content.v1.tar+gzip` media type, but the
  Palette-managed target cluster's controller can't resolve
  `harbor.harbor.svc.cluster.local` (it's in Palette's cluster, not the
  target's). Same class of issue as the ChartMuseum attempt below.
- **Standalone ChartMuseum in Palette's cluster** — same DNS-reachability
  problem. Would work if exposed via a public-facing LoadBalancer / Ingress
  on the Palette cluster, but at that point GitHub Pages is simpler.
